# 7×24 小时长期运行风险分析报告

> 分析对象：[`congmingpay`](main.go:1) 项目
> 分析目标：评估 7×24 小时不间断运行是否会出现错误、内存异常占用、电脑卡顿等问题
> 分析方法：源码审查，聚焦 goroutine 生命周期、内存累积、资源释放、日志/数据库增长

---

## 一、总体评估

项目整体设计**较为健壮**，多数长期运行风险已有防护措施。但存在 **2 个中风险**和 **3 个低风险**问题，在极端场景下可能影响长期运行稳定性。

| 风险等级 | 数量 | 说明 |
|----------|------|------|
| 🔴 高风险 | 0 | 无致命问题 |
| 🟡 中风险 | 2 | 运行期间无定时清理任务历史；printLocks 无限增长 |
| 🟢 低风险 | 3 | 日志单文件无大小上限；SQLite WAL 文件增长；离线任务永久等待 |

---

## 二、已具备的防护措施（做得好的部分）

### 2.1 ✅ Goroutine 生命周期管理完善

| 组件 | 机制 | 评价 |
|------|------|------|
| [`dispatch`](internal/printsvc/Service.go:222) | 迭代非递归循环 + `e.gen` 代次守卫 + `e.cancelled` 标志 + `e.wake` channel | **优秀**：避免栈无限增长，Retry/Cancel 能正确终止旧 goroutine |
| [`monitorLoop`](internal/ui/StatusMonitor.go:83) | `stop` channel + 每轮 select 检查 | **优秀**：删除/重建打印机时正确停止旧监测线程 |
| [`stateLoop`](internal/mqtt/Client.go:207) | `stop` channel + `time.NewTicker` + `defer t.Stop()` | **优秀**：随连接生命周期，Close/Reload 正确停止 |
| [`alertTickLoop`](internal/ui/AlertWindow.go:238) | `notifyReady` atomic 标志退出 | **良好**：程序退出时停止 |
| [`rotateLoop`](internal/logger/Logger.go:89) | `stopCh` channel + `time.NewTimer` + `t.Stop()` | **优秀**：日志轮转 goroutine 正确管理 |

### 2.2 ✅ 日志轮转已实现

[`logger`](internal/logger/Logger.go:1) 已实现按天分文件 + 保留 7 天自动清理：
- `log\<yyyy-MM-dd>.log` 按天切换
- `pruneLocked` 每天清理超过 7 天的日志
- 跨天切换与写入共用互斥锁，不丢行

### 2.3 ✅ 告警窗条目有上限

[`AlertWindow`](internal/ui/AlertWindow.go:38) 的 `alertMaxItems = 200`，超出丢最旧，不会因告警风暴无限增长。

### 2.4 ✅ SQLite 连接管理

[`Store`](internal/printsvc/Store.go:31) 设置 `SetMaxOpenConns(1)`，WAL 模式，`Close` 方法正确关闭。`main.go` 有 `defer svc.CloseStore()`。

### 2.5 ✅ 任务终态落盘

[`setStatus`](internal/printsvc/Service.go:500) 在 Done/Failed 时立即 `flushPersist`，降低崩溃丢单风险。

### 2.6 ✅ 配置损坏健壮性

[`main.go`](main.go:60) 配置加载失败时备份坏文件 + 默认配置启动，不会因配置损坏崩溃。

## 三、风险点详细分析

### 🟡 风险 1：运行期间无定时清理任务历史（中风险）

**位置**：[`Persist.go`](internal/printsvc/Persist.go:35) `PruneHistory`

**问题**：
`PruneHistory` 只在两个时机调用：
1. [`RestoreAndResume`](internal/printsvc/Persist.go:64)（程序启动时）
2. [`SetHistoryDays`](internal/printsvc/Persist.go:15)（用户修改保留天数时）

**运行期间没有定时调用 `PruneHistory`**。这意味着：

- 已完成/失败的任务在内存 `s.entries` 切片和 SQLite `jobs.db` 中**持续累积**，直到下次重启。
- 高频打印场景（如繁忙餐厅每天数百单），7 天不重启可能累积数千条任务记录。
- 每条 `entry` 持有 `data []byte`（ESC/POS 字节）和 `sourceJSON []byte`（JSON 源），单条可能数 KB。

**影响**：
- **内存**：数千条任务 × 数 KB/条 = 数 MB ~ 数十 MB，不会导致系统崩溃，但属于不必要的内存占用。
- **数据库**：`jobs.db` 文件持续增长，`LoadAll`（重启恢复）耗时增加。
- **UI 响应**：[`Jobs()`](internal/printsvc/Service.go:130) 每次返回全量快照，任务列表过长时 UI 刷新可能变慢。

**建议**：
在 `Service` 中增加定时清理 goroutine（如每小时调用一次 `PruneHistory`），或在 `Submit` 时按条数阈值触发清理。

---

### 🟡 风险 2：printLocks 的 sync.Map 无限增长（中风险）

**位置**：[`Service.go`](internal/printsvc/Service.go:96) `printLocks sync.Map` + [`printerLock`](internal/printsvc/Service.go:100)

**问题**：
`printerLock` 使用 `LoadOrStore` 懒创建每台打印机的串行锁，但**从不调用 `Delete`**（搜索确认无 `printLocks.Delete` 调用）。

```go
func (s *Service) printerLock(id string) *sync.Mutex {
    v, _ := s.printLocks.LoadOrStore(id, &sync.Mutex{})
    return v.(*sync.Mutex)
}
```

当云端不断下发带新 IP 的打印消息时（[`api.Process`](internal/api/Print.go:1) 的自动登记逻辑会 `UpsertPrinter`），每台新打印机都会在 `printLocks` 中创建一个条目。如果打印机被删除（[`config`](internal/config/Config.go:1) 的 `RemovePrinter`），对应的锁条目**不会被清理**。

**影响**：
- **实际风险较低**：打印机数量通常有限（几台到几十台），即使有云端自动登记，IP 变化频率不高。
- 但在极端场景（如 DHCP 频繁分配新 IP + 自动登记），长期运行可能累积数百个无用锁条目。
- 每个条目仅一个 `*sync.Mutex`（约 8 字节指针），内存影响微乎其微。

**建议**：
在删除打印机时（`RemovePrinter`）调用 `printLocks.Delete(id)`，或在 `PruneHistory` 时顺带清理不在当前打印机列表中的锁。

---

### 🟢 风险 3：日志单文件无大小上限（低风险）

**位置**：[`Logger.go`](internal/logger/Logger.go:1)

**问题**：
日志按天分文件 + 保留 7 天，但**单日文件无大小上限**。高频场景下（如每秒多条状态日志 + 丢包统计），单日日志可能达到数十 MB。

**影响**：
- 7 天 × 数十 MB = 数百 MB 磁盘占用，对现代电脑影响不大。
- 但 `StatusMonitor` 每秒 ping + 丢包统计日志，在多台打印机 + 网络不稳定时，日志量可能超预期。

**缓解因素**：
- 丢包统计有节流（无丢包不输出，5 分钟一条）
- 抖动日志有 60 秒节流
- 状态变化才记日志（不是每秒都记）

**建议**：
可考虑增加单日文件大小上限（如 50MB），超限后停止写入非 Error 级别日志。但当前设计在正常场景下可接受。

---

### 🟢 风险 4：SQLite WAL 文件增长（低风险）

**位置**：[`Store.go`](internal/printsvc/Store.go:41) `journal_mode(WAL)`

**问题**：
SQLite WAL 模式下，`jobs.db-wal` 文件会随写入增长，正常情况下 SQLite 会在 checkpoint 时合并回主库。但 `SetMaxOpenConns(1)` + 长期运行，如果 checkpoint 不及时，WAL 文件可能持续增大。

**影响**：
- WAL 文件通常在几 MB 内，SQLite 会自动 checkpoint（默认每 1000 页或最后连接关闭时）。
- 长期运行不关闭连接，WAL 可能增长但不会失控。

**建议**：
可定期执行 `PRAGMA wal_checkpoint(TRUNCATE)` 主动回收 WAL 空间。但当前设计风险较低。

---

### 🟢 风险 5：离线任务永久等待（低风险，设计如此）

**位置**：[`waitAndContinue`](internal/printsvc/Service.go:333)

**问题**：
打印机离线时，任务进入 `JobWaiting` 状态，**永不自动失败**，持续等待联通。这是**设计意图**（CLAUDE.md 明确：「离线不失败，联通即打，永不自动失败」），但意味着：

- 如果一台打印机永久离线（如报废、IP 变更），其等待任务会**永久驻留**内存和数据库。
- 每个等待任务持有一个 goroutine（在 `waitAndContinue` 的 `select` 中阻塞），虽然阻塞的 goroutine 占用极少资源（约 2-8 KB 栈），但数量过多仍有累积。

**影响**：
- 正常场景：打印机恢复后任务立即完成，无问题。
- 异常场景：多台打印机永久离线 + 持续收到打印消息 → 等待任务无限累积。

**缓解因素**：
- `PruneHistory` 只清理 Done/Failed，**不清理 Waiting**（设计如此，CLAUDE.md：「排队中与等待重试不受限」）。
- 实际餐厅场景打印机数量有限，离线任务累积速度可控。

**建议**：
可考虑增加「等待任务超时自动失败」的可选配置（如 24 小时未送达则失败），但需与产品需求确认。当前设计在正常场景下可接受。

## 四、内存占用估算

### 4.1 常驻内存（固定）

| 组件 | 估算 | 说明 |
|------|------|------|
| Go 运行时 + Walk 框架 | ~15-25 MB | 基础开销 |
| SQLite 连接 | ~2-5 MB | modernc 纯 Go 实现 |
| MQTT 客户端 | ~1-2 MB | paho 库 |
| UI 控件 + 表格模型 | ~3-5 MB | Walk 窗口/控件 |
| **小计** | **~20-35 MB** | 稳定不增长 |

### 4.2 可变内存（随运行时间增长）

| 组件 | 单条大小 | 日增量估算 | 7天不重启 |
|------|----------|------------|-----------|
| `s.entries` 任务列表 | ~5-20 KB | 100-500 条/天 | 700-3500 条 = 3.5-70 MB |
| `printLocks` | ~8 字节/台 | 取决于打印机数 | 几十台 = 可忽略 |
| `online` 注册表 | ~100 字节/台 | 固定 | 可忽略 |
| 告警窗条目 | ~200 字节/条 | 上限 200 条 | 上限 40 KB |

**结论**：7 天不重启，可变内存主要来自任务列表累积，最坏情况约 **70 MB**，加上常驻约 **100 MB** 总量。对现代电脑（通常 8GB+ 内存）**不会导致卡顿**。

## 五、Goroutine 数量分析

| 组件 | 数量 | 生命周期 |
|------|------|----------|
| `monitorLoop` | 每台打印机 1 个 | 随打印机增删 |
| `dispatch` | 每个任务 1 个 | 任务终态后退出 |
| `stateLoop` | 1 个 | 随 MQTT 连接生命周期 |
| `alertTickLoop` | 1 个 | 程序生命周期 |
| `rotateLoop` | 1 个 | 程序生命周期 |
| paho MQTT 内部 | 数个 | 随连接生命周期 |

**关键风险**：`dispatch` goroutine 在任务 `JobWaiting` 时**不退出**（阻塞在 `waitAndContinue` 的 select 中）。如果大量任务等待离线打印机，goroutine 数量 = 等待任务数。

**正常场景**：10 台打印机 × 每台几个等待任务 = 几十个 goroutine，完全可接受。
**极端场景**：数百个等待任务 = 数百个 goroutine，每个约 2-8 KB 栈 = 1-4 MB，仍可接受。

## 六、结论与建议

### 6.1 总体结论

项目**可以安全地 7×24 小时长期运行**，在正常餐厅场景下不会出现内存异常占用或电脑卡顿。主要原因是：

1. Goroutine 生命周期管理完善，无泄漏风险
2. 日志有轮转和清理
3. 告警窗有条目上限
4. 任务终态正确落盘和退出

### 6.2 建议改进项（按优先级）

| 优先级 | 改进项 | 风险等级 | 建议 |
|--------|--------|----------|------|
| P1 | 增加定时 `PruneHistory` | 中 | 在 `Service` 中增加每小时清理一次的 goroutine |
| P2 | 删除打印机时清理 `printLocks` | 中 | 在 `RemovePrinter` 时调用 `printLocks.Delete` |
| P3 | 日志单文件大小上限 | 低 | 超限时降级非 Error 日志 |
| P4 | 定期 SQLite WAL checkpoint | 低 | 每小时执行 `PRAGMA wal_checkpoint(TRUNCATE)` |
| P5 | 等待任务超时机制 | 低 | 可选配置，24h 未送达自动失败（需产品确认） |

### 6.3 运维建议

- **建议每周重启一次**程序（如凌晨低峰期），可彻底回收所有可变内存。
- 关注 `jobs.db` 文件大小，如超过 50 MB 可手动清理。
- 关注 `log\` 目录大小，正常应控制在 100 MB 以内（7 天）。
- 如发现内存持续增长，优先检查是否有打印机长期离线导致任务累积。
